# 曲措乡 · 代码瘦身与维护方案

> 本文所有数字都是 `import` 图与行数实测，不是印象。测量脚本思路见文末。
> 规模：src 下 203 个 js/jsx（含 30 份测试），非测试代码 **42,590 行**。

---

## 一、先说结论：真正的问题只有一个半

不是"文件太多"，203 个文件对这个体量是合理的。问题在**依赖形态**：

| 指标 | 实测 | 判断 |
|---|---|---|
| `MudRPG.jsx` 出度 | **125** 个模块 | 上帝组件，唯一的真问题 |
| `MudRPG.jsx` 体量 | 4693 行 / 96 useState / 45 useEffect / 91 useCallback | 同上 |
| `InnScreen.jsx` 入度 | **19** | 架构错位，半个问题，但极好修 |
| 其余入度最高者 | equipment 23 · overlayClose 17 · mvu 13 | 正常的核心枢纽，不用动 |

**别做的事**：不要为了"文件数好看"去合并模块。这个项目这一年踩的坑，绝大多数是
*同一件事散在多处、改一处漏一处*（四份特效词典、三处 carry 白名单、两套形态状态、
图鉴的分组白名单）。合并**同类职责**有价值；合并**不同职责**只会制造新的上帝模块。

---

## 二、方案（按 收益/风险 排序，可独立执行）

### 1. 拆 `MudRPG.jsx`（收益最大，风险最高，必须分批）

4693 行里混着四类东西，它们的变更频率完全不同：

| 类别 | 大致占比 | 该去哪 |
|---|---|---|
| 状态声明（96 个 useState） | ~10% | 按域拆成自定义 Hook |
| 副作用（45 个 useEffect） | ~20% | 跟着各自的状态域走 |
| 业务 handler（91 个 useCallback） | ~50% | 按域拆成 `src/handlers/*.js` 纯函数 + 薄包装 |
| JSX 装配 | ~20% | 留在 MudRPG |

**分批顺序**（每批独立可验证、可回滚）：

1. `useNpcPresence()` — room.npcs 的注入/回填/涌现（已有 `roomNpcs.js` 做纯函数，只差把 effect 收进去）
2. `useHomestead()` — 箱子/酒窖/菜畦的读写（`homestead.js` 已是纯函数）
3. `useCompanion()` — 队友出战/形态/立绘
4. `useBuildingActions()` — 客栈/医馆/商店那批 handler（它们只依赖 char.money + act）
5. 最后才动 `act()` 主循环——它是全项目最脆的一段，单独一批，前四批稳定后再说

**硬约束**：每批**只搬不改**。搬完 `npm run verify` 必须绿，行为差异一律视为 bug。
不要顺手"优化"——这个项目已经有多次"顺手改"引入回归的记录。

**收益**：出度从 125 降到 ~40；每个 Hook 有自己的测试面；新人能只读一个域。

---

### 2. 抽 `Overlay/Header/Btn` 出 `InnScreen`（收益高，风险几乎为零，先做这个）

现状：19 个文件 `import { Overlay, Header, Btn } from "./InnScreen.jsx"`。
客栈屏一改，19 个界面全部连坐重新打包；读代码的人也会以为它们跟客栈有关系。

**做法**：新建 `src/ui/Overlay.jsx`，把三个组件搬过去，`InnScreen` 改为从那儿 import。
一次 sed 能改完 19 个文件，`verify` 兜底。

**收益**：InnScreen 入度 19 → 1；`src/ui/` 从此是"通用组件"的明确去处，
以后再有共享组件不会又寄居到某个业务屏里。

---

### 3. 清死文件（低收益，零风险，顺手做）

`import` 图里零入度且非入口的：`memory/activityLog.js`、`memory/memoryWrite.js`
（只在 docs 与 version.js 的变更记录里被提到，无代码引用）。
`PresetEditor.jsx` / `buildings/BuildingPanel.jsx` / `quests/questHarness.js`
在 MudRPG/SettingsPanel 里有字符串提及，**删之前必须逐个确认是不是动态引用**。

配一条守卫：`import` 图零入度且不在入口白名单 → 测试红。让死文件不能再悄悄堆积。

---

### 4. 把"白名单模式"从机制上消灭（收益最高的**预防**措施）

这个项目**反复栽在同一个模式**上，值得单列：

| 事故 | 白名单在哪 | 后果 |
|---|---|---|
| 图鉴只显示 17/246 招 | `SKILL_GROUP_LABEL` 当成过滤条件 | 六个门派静默消失 |
| 四份特效词典 | 每处各维护一份键名 | 加特效漏一处＝界面空白 |
| 老七进玩家家 | 落点池取全集，没排除锁房 | 契诃夫之枪失效 |
| 邀请按钮消失 / 食物 buff 不出现 | 字段没进传播白名单 | 功能静默失灵 |

**通用解法**：凡是"一张表决定什么东西能出现"，一律改成**默认放行 + 显式排除**，
而不是默认丢弃 + 显式允许。查不到配置时用兜底值（如 key 本身）继续渲染，
**绝不静默过滤**。`moveCodex.js` 的分组名就是照这个改的，可作模板。

配套：每个"注册表"都要有一条`总数对账`测试——源表 N 条，出口必须也是 N 条。

---

### 5. 守卫测试的维护（已经有 634 条，别让它腐烂）

现在的测试有个**新风险**：豁免名单腐烂。上一轮就发现 `LEGACY_MISSING_CATEGORY`
挂着早已修好的两个人——不再掩盖任何问题，却会静默吞掉未来的回归。

**规矩**：每加一条豁免名单，必须同时加一条"名单不得腐烂"的反向测试
（登记在册的欠账必须真的还欠着）。`strongholdWiring.test.js` 与
`musicPlayer.test.js` 的 `KNOWN_MISSING` 已经是这个写法，照抄即可。

---

### 6. 文档与代码的对账（已有，建议扩面）

`docsTree.test.js` 已经在管"文件树登记完整 + 无幽灵条目 + 文件数一致"，
这三条救过好几次场（这轮删 `moveExplainer.js` 就是它抓到我忘了删登记）。

建议扩两条：
- `version.js` 已 2204 行，占非测试代码 5%。切成 `version/2026-07.js` 按月归档，
  只保留最近 20 条在主文件（它每轮都在变更，是 diff 噪音的最大来源）。
- 新增模块必须在文件树里有一句话描述——现在只校验"存在"，不校验"有描述"。

---

## 三、执行顺序建议

```
第 1 步  抽 Overlay/Header/Btn（半天，风险≈0，立刻见效）
第 2 步  清死文件 + 加零入度守卫（半天）
第 3 步  version.js 按月归档（半天，大幅降低 diff 噪音）
第 4 步  拆 MudRPG 第 1~4 批 Hook（每批一天，各自独立可回滚）
第 5 步  act() 主循环（单独排期，前四批稳定之后）
```

前三步加起来一天半，能把"看代码的人被吓到"的部分先解决掉；
第 4 步是真正的结构改善；第 5 步不着急，`act()` 现在是能跑的，别为了好看去动它。
