## 2. Lazy-Stage 整改规划（已审计，未改）

### 病根
任务系统里**「战斗」不是一等公民**。只有 4~5 个 stage 通过 `choices:[{resolve:"combat", combatNpc}]` 挂了真战斗（村1 s2、扎西 s3_hunt、村4 s3、山1 s1）。其余凡剧情需要打的，作者只写了 description 文字 + `completionFlag` + `onReach` 奖励，**指望 AI 在叙事里"演"出打斗** —— AI 当然一笔带过、flag 一打完事。这与铁律「系统裁决」背道而驰：把「打没打赢」这个数值裁决交给了 AI 叙事自由。

**实例（用户实测踩中）**：玉泉寨·任务一·小牧童的牦牛 `s1_rescue`，description 明写"击退野狼后牦牛认人"，但零战斗机制，AI 直接叙事秒杀三狼、flag 完成。用户原话："需要打，别不是真打吧""不要 flag"。

### 审计结果（脚本 audit：🟢有机制 15 / 🔴🟡可疑 44）
分三类：

**第一类 · 硬核战斗被 flag 糊弄（最严重，必须真打却零机制）**
- 玉泉寨·任务一·小牧童的牦牛 `s1_rescue` —「击退野狼」← 用户踩中
- 神兵·虎王猎场 `s3_liesha_huwang` —「猎杀吊睛虎王（回合制 boss 战），红档，专属技能扑咬/虎啸」全游戏最该真打的，现在是 flag
- 神兵·地宫问心 `s2_sanchang_qiecuo` —「三场连续切磋（绿档→…）」；`s3_sanwen` 还写"通过战斗后"但前面没战斗
- 玉泉寨·任务四·卓玛的青稞酒 `s1_hunt`（type=KILL）—「猎杀银灰独眼狼王」KILL 类型却没挂 targetTag+combatNpc
- 山4·管家的通缉令 `s2_ambush` —「亡命徒摸黑进谷」伏击战

**第二类 · 该真打但设计成"可打可不打"（机制缺战斗分支）**
- 玉泉寨·任务二·李若由的商队账 `s1_confront` —「或直接武力威胁」无 combat choice
- 全收集隐藏线 `s2_steal_back` —「夜闯土司府，管家会挡在前面」潜入战被 flag 带过
- 山3.5·劫药 `s1_negotiate` — 巴桑横刀，有 talk 无后备 combat

**第三类 · 误报（本就不该真打，关键词扫宽了，正常）**
- 各线 `sX_cg_moment`、送虎胆到土司府、虎1/虎2/虎3 嘎则线、山2 妹妹的消息、官1 查案、神兵各线"拔剑触发幻象/三问/枯骨残念"（明写"不是战斗，是三问"）—— 情感/CG/问心节点，**不动**。

### 整改方向（下轮拍板后动手）
给 stage 增加**一等的战斗触发机制**。建议做**通用框架**而非逐个手搓：

```
stage.combat = {
  npc: { name, levelCap, tag },   // 或 npcs:[…] 支持"三场连续切磋"
  mustWin: true,                   // 打赢才 forceAdvance，输/逃不推进
  reward: { … }                    // 复用现有 onReach
}
```
推进到该 stage 时**强制进 DuelScreen**，复用现有 `triggerQuestChoice` 里 `resolve:"combat"` 的那套（`ensureNpcCombatData` 现造 foe + `pendingQuestBranch` 认领 + onFinish 里 win 才 forceAdvance）。第一类挂上去、第二类补 combat 分支、第三类不动。

**要用户拍板**：boss/连续切磋是逐个手搓 combatNpc，还是做通用框架让每 stage 只声明"打谁/什么档/赢了给什么"。（建议后者，一次做对，十几个能批量挂。）

### §2 遗留：AI 自吐 p.choices 绕过门槛
`MudRPG.jsx` 有**两套选项 UI**：① 面板 `availableQuestsHere`（受 E 位置门槛管）；② AI 在回复里自吐 `p.choices`（第 ~2304 行，完全不受门槛管）。E 只堵了 ①。若实机发现三选一是 AI 从叙事里 ② 吐的，需在 system prompt 层把位置门槛作为硬约束注入，或让 stage 推进本身加位置门槛（比选项显示更根本）。

## 3. 赌石系统设计（纯设计，未写代码）

### 3.1 定位与背景（架空本地化）
- **参考现实**：赌石 = 滇缅边境翡翠原石交易，"一刀穷，一刀富，一刀穿麻布"。原石裹皮壳，肉眼难断（"神仙难断寸玉"），凭皮壳表现估价，切开定生死。**关键赌性**：开切位置影响结果——同一石头大头切/小头切可能天差地别。
- **本作定位**：**架空**，直接用「翡翠」概念（用户确认用翡翠，不必强行改河料玉）。
- **选址**：**天都镇**（用户指定）。天都镇是设定里最繁华市镇、有地下渠道黑市气质，已有「玉器轩」(ANTIQUE, shopKey 玉器轩)。料场紧挨玉器轩，行当对味。挂法：新增一个 building（见 3.4），进天都镇即可访问（或先做成天都镇内层房间/一个 building 入口，守固定拓扑铁律，不新增外层地图节点）。

### 3.2 核心玩法（用户确认的确切规则）
1. **花钱进石头**：玩家付银两买一块原石进场。
2. **石头出生即固化**：石头一出现，系统**当场骰定并写死**「哪个位置有料、哪个位置没料、料的品质」——存进石头对象，玩家不可见。（同 NPC 出生固化哲学。）
3. **开三次位置**：这块石头可以开**三刀**，每刀选一个位置。是否切中"有料位置"由出生时固化的分布决定。**每一刀都要 AI 叙事**（描述这一刀切下去见到什么），但**切中与否是系统裁决**，AI 只描述系统给的结果。
4. **每刀后有人收购**：每开完一刀，**有收购人出价**（AI 扮演收购人叙事、给个价），玩家决策：
   - **卖出** → 拿钱走人（落袋为安，对应真实"切涨就卖"）。
   - **据为己有** → 留着自己用（进下一步做装备）。
5. **据为己有 → 委托料场做装备**（付手工费）：
   - **30% 被偷**（料场黑，料没了）
   - **10% 失败**（做坏，料废）
   - **60% 做好** → 出装备。**装备品质概率 = f(翡翠品质 + 手工费高低 + 运气)**。
6. **运气关联概率**：**已有现成设计**，见 3.3。

### 3.3 运气概率——复用已有设计（重点，别重造）
`src/equipment.js` 的 **`qualityDistribution(luck)`** 就是"关联运气的概率"：
```
气运 0（基础）：白50 绿30 蓝10 紫8  橙1.5 红0.5   BASE_DIST=[50,30,10,8,1.5,0.5]
气运 10（顶峰）：白0  绿20 蓝20 紫20 橙20  红20    PEAK_DIST=[0,20,20,20,20,20]
线性插值 t = 气运/10，始终合计 100%。
rollQuality(luck) 按此分布抽一档品质。
```
**赌石做装备的品质**就用这个函数，但要在 luck 基础上叠加「翡翠品质加成」和「手工费加成」：
```
有效 luck' = 玩家气运 + 翡翠品质档位加成 + floor(手工费 / 某阈值)   （clamp 0~10）
成品品质 = rollQuality(luck')   ← 60% 做好分支里跑这个
```
具体加成系数下轮和用户敲定。**成品装备**用 `makeGameItem(spec)`（= `makeItemSmart` + `makeItem`）造，数值由品质自动算（系统裁决）。

### 3.4 与现有系统的接口（全部有实证参照）
- **building 框架**：新增 `BUILDING_TYPE.GAMBLESTONE`（或复用现有枚举），在 `qucuoBuildings.js` 天都镇下加一条 `{ id:"gamblestone_tiandu", name:"赌石料场", type:… }`。在 `MudRPG.jsx` ~3929 行 ForgeScreen 那一段旁边，加 `activeBuilding.type === … && <GambleStoneScreen … inline … />`。
- **"委托做装备"直接抄 `ForgeScreen.jsx` 模板**：它已经是"付手工费 → flag 记 pending → 延时 → 取件时按 luck 骰品质 makeGameItem 进背包"的完整先例。赌石的「据为己有→委托」几乎是它的变体，把"取件骰品质"换成"30/10/60 三分支 + rollQuality(luck')"即可。参照 `handleForgeCommission` / `handleForgePickup`（MudRPG 3187/3194）。
- **经济**：银两买石、手工费、卖石收入走 `char.money`。成品/中间料入 `items/catalog.js` 品质定价体系。
- **七维接入**：气运→切涨概率 & 成品品质；悟性→皮壳线索清晰度（可选）；智谋→识破假料（可选进阶）。让七维在此有真实作用。
- **神兵线钩子**：高品质翡翠成品可作某件神兵/装备的稀有材料，给"暴富之外的意义"，避免沦为纯赌博小游戏。

### 3.5 引导任务（从一个任务一点点引到赌石，用户要求渐进）
四步，每步**真做事**（不 lazy）：
1. **偶遇引子**：玩家在天都镇（或料场门口）撞见一个刚"切垮"的老料工（新 NPC，暂名「石老倌」），对着开了窗却空无一物的废料发呆。对话中第一次听说赌石和"一刀穷一刀富"。
2. **学看皮壳**：石老倌给小任务——辨认几块石头的皮壳表现（松花/蟒带/癞）。教玩家读皮壳线索（对应真实"看货"）。做对认你是块料。
3. **第一次下注（低风险）**：他给一块他不敢切的小料，让你练手切一刀，系统骰（受气运/悟性），亲身体验切涨/切垮。
4. **解锁料场 building**：切完这一刀，料场正式开放，以后自由赌。

**注意**：这条引导任务本身也要按 §2 的整改标准做——"切一刀"是真机制（系统骰 + AI 叙事），不是 flag。

### 3.6 每步都要 AI 叙事、AI 判断的分工（守铁律）
用户强调"每一步都需要 AI 来叙事，来判断"。**边界**：
- **AI 叙事**：描述皮壳外观、开切时见到什么（绿/水/棉/裂）、收购人的神态与话术、做装备的过程。
- **AI 判断**：收购人出价的合理性（在系统给的价格区间内润色）、皮壳线索的文学化呈现。
- **系统裁决（AI 绝不碰）**：石头哪里有料（出生固化）、切中与否、收购基准价、30/10/60 三分支骰、成品品质 rollQuality。
- 这条线一旦让 AI 决定"切没切中/做没做成"，就是重蹈 lazy-stage 覆辙。务必系统骰、AI 只描述。

### 3.7 下轮要用户拍板的点
1. 手工费→有效 luck 的加成系数、翡翠品质→luck 加成的具体数值。
2. "开三次位置"的位置模型：是抽象成"3 个格子，出生时标好哪个有料"，还是做"大头/小头/中间"这种带真实感的切法（命中概率不同）？
3. 收购人每刀出价的定价公式（基于已开出的料 + 剩余未开的期望）。
4. 石老倌是否配完整支线（他当年赌垮的往事），还是纯功能引导人。
5. building 是独立 `GambleStoneScreen.jsx` 还是并进玉器轩。

## 5. 任务提示（playerHint）功能设计（用户要求，未实现）

### 5.1 需求
用户原话："任务要给任务提示，在最下面。每个 stage 都要写，在任务面板也要标记，也写到 md，手工。"

拆解：
1. **每个 stage 手写一条面向玩家的提示**（`playerHint`）——告诉玩家这一步该往哪个方向做/说/去哪，但**不能剧透答案**（尤其说服类，不能直接把突破口念出来）。
2. **显示在最下面**：主界面/任务区底部给玩家看这条提示。
3. **任务面板也要标记**：`◈行动抉择`/`❢`那块，把当前 stage 的 hint 一并标出来。
4. 手工逐条写，不自动生成。

### 5.2 现状缺口
- stage 现在只有 `description`（给 AI 看的剧情推进文本，注入 prompt 的 questStageNote），**没有面向玩家的提示字段**。
- `collect` 类有 `hint`（如"白塔往雪山高处的石缝间"），但那是采集专用、且混在 collect 结构里，不通用。
- 说服类 `persuade.keys[].hint` 是给 AI 判定用的，对玩家隐藏。

### 5.3 落地方案（下轮）
1. **stage 加字段 `playerHint`**（字符串，手写）。与 `description`（给 AI）分离：`description` 是"这一步剧情是什么"，`playerHint` 是"玩家该怎么推进"。
   - 例（村1 s1_hear）：`playerHint: "老猎户提到熊山口出了事——去大草甸的熊山口看看到底怎么回事。"`
   - 例（村1 s2_choice）：`playerHint: "熊山口管家手下正在讹人，你可以动手、讲理、或旁观。"`
   - 说服类（村3 s1a）：`playerHint: "老孙嘴上说怕村里人看不起，试着聊聊他到底在怕什么、想想他自己当年的经历。"`（点方向，不报突破口 id）
2. **主界面底部展示**：在 `availableQuestsHere` 渲染区（或专门的底部提示条）显示当前每个可推进 stage 的 `playerHint`。位置"在最下面"——即输入框上方或任务区末尾。

## 8. 说服系统重构（戒心值 + 线索解锁）——✅ 本轮已实现

### 8.1 最终机制（用户逐轮拍板定稿）
一套**戒心值**驱动，配三段式因果：

**戒心值（guard）**——一套数值，初始 100，越低越松口：
- 每轮玩家说话，AI 评估这话让 NPC 放下多少戒备：
  - 普通话术（讲道理、一般寒暄）→ 固定小降（建议 **10**）
  - **聊美了**（真诚、投机、示弱、给好处、说到情绪点上）→ 大降（建议 **30~50**）
- **每跨过一个 30 的坎（即戒心降到 70 / 40 / 10）→ 解锁一条心结线索**，显示在上边（把某个突破口的方向透露给玩家）。线索按 keys 顺序逐条解锁。

**命中突破口（hitKeys）——定成败，与线索解锁解耦**：
- 玩家说中某个突破口就算命中，**不管线索解没解锁**（用户拍板："都算"——歪打正着也算，线索只是帮迷茫玩家知道往哪说）。
- 命中数 ≥ `resistance`（通常 2）→ 说服成功（yield）。

**三者关系**：
- 戒心 = 破冰进度，喂线索（辅助）。
- 命中 = 戳中心结，定成败（核心）。
- "聊美了"这一下通常既大降戒心、又常顺带命中（因为聊到点上往往就是戳中了），但两者判定分开：戒心降幅 + 是否命中，AI 分别给。
- 三种拿线索的方式（用户原话）：戒心到坎、聊美了（触发大降进而到坎）、直接问（问本身算一种破冰话术，也降戒心）。

### 8.2 判定流程（每轮）
AI 在说服 system prompt 里，除了原有的短台词 + `hit`，**新增输出 `guardDrop`**（这话让戒心降多少，AI 按话术质量给 10~50）：
```
{"hit":"key_id或null", "guardDrop":10~50, "yield":true/false}
```
系统侧 `runPersuadeTurn` 结算：
1. `newGuard = max(0, guard - guardDrop)`
2. 跨过 30 坎 → 解锁对应序号线索，push 进 `unlockedHints`
3. `hit` 合法则加进 `hitKeys`（合法性放宽：**去掉 need-flag 锁死；歪打正着也算**，见 8.3）
4. `yield = hitKeys.length >= resistance && AI说yield`
返回 `{ line, hit, guardDrop, newGuard, newHitKeys, unlockedHints, yield }`。

### 8.3 判定放宽（解决"太钝、迟迟说不中"）
现有 `buildPersuadeSystem` 判定过严导致玩家一直 null。改：
- **去掉 need-flag 硬锁**对命中的否决（用户："都算"）——need 线索仍可作"解锁提示"用，但不再阻止命中。
- system prompt 里判定标准放宽：玩家的话**只要方向对、沾到心结的边**就可判 hit，不要求字字精准。宁可偏松，避免玩家空谈五六轮还是 null 的挫败。
- 保留"重复已中的不计"。

### 8.4 UI（PersuasionScreen）
- **顶部显示戒心值条**（或"神色"文字档：油盐不进→有所松动→几乎卸下防备）。
- **已解锁线索列在上边**（用户："上边 hint 显示"）：每解锁一条，显示"你看出：他似乎在意……（某方向）"。未解锁的不显示。
- 保留现有的进度反馈文字。

### 8.5 不继承 / 不保存修复（同轮一起做）
现状：`turns`、`hitKeys` 是 PersuasionScreen 组件内 useState，`onFinish` 即销毁 → 再点从头开始、对话不进存档。
修：把说服进度 `{ guard, hitKeys, unlockedHints, turns, done }` 提到 **`persuasionProgress[questId+flag]`**（MudRPG 顶层 state，进快照持久化）。PersuasionScreen 打开时读回上次进度续接；每轮结算写回。关闭/存档都带上。

### 8.6 落地文件
- `src/quests/persuasion.js`：加 `guardDrop` 输出与解析、戒心结算、线索解锁、判定放宽。
- `src/PersuasionScreen.jsx`：读写外部 persuasionProgress、顶部戒心条、线索显示。
- `src/MudRPG.jsx`：新增 `persuasionProgress` state + 进快照 + 传给 PersuasionScreen。
- 各 persuade 结构：确认 `keys` 顺序即线索解锁顺序；`resistance` 保持 2。

### 8.7 数值待微调（实现时先用建议值，跑一场再调）
- 普通话术降 10 / 聊美了降 30~50。
- 100→70→40→10 三条线索坎。
- resistance = 2。
- 这套数值意味着：玩家大约 2~3 轮好话能拿第一条线索，全程 5~7 轮能通关，避免太吾式的冗长拉锯。
