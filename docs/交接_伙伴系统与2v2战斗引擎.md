## 二、伙伴系统设计背景（作者原话摘要）

作者要求："把雪豹插入进去，作为打手/队友，思考一下入队逻辑，仿照宝可梦的2v2逻辑"，随后
明确是"真正2v2：玩家+雪豹同时在场，每回合两方各自选招，对面也可能是2个单位"，"可以选择
队友托管或者我来控制，控制的话，我控制俩人都要能选是哪一个敌人为目标"。

作者亲自写了雪豹的专属武学「雪隐三绝」全文（含攻击/防御/状态三招的完整白话古文描述），
入队方式也是作者定的："雪豹一开始在村口，作为npc，面板除了官方六个，单独一个邀请入队按钮，
点了就能入队结算，ai叙事写的prompt（角色描述）是前世的羁绊，认准了你是这片雪域高原的
主人，忠贞无二"。

**几个关键决策（已跟作者确认，不要再问一遍）**：
- 只剩一个敌方目标时自动锁定，不用玩家选
- 雪豹托管时是"纯野兽本能"，高攻击/高风险偏好，**不会**特意配合玩家战术
- 敌方AI选目标随机分散，不做集火策略
- 若同伴（雪豹）把玩家选定的目标打倒了，玩家原目标已死，**自动转移**到另一个存活敌方目标
  （不是打空气，也不是重新弹窗问玩家）
- 2v2里"防御也要指定目标"——不是泛用姿态。若A打B而B这回合的招指向的不是A（B在忙着打
  别人，或B的防御防的是别人），对A来说B此刻**没有防御姿态**（"裸奔"），这是本引擎最核心
  的设计取舍，见 §五
- 现有战斗引擎（`resolveTurn.js`）只有攻击/防御/状态三角相克，**没有闪避/隐身免命中**这个
  维度。雪豹的"融雪"（隐身/闪避设定）套`防守反击`原型、"冰川步"（闪避/连击站位）套`蓄势`
  原型——文本保留作者写的隐身/闪避描述，机制上是减伤/蓄力。这是跟作者明确确认过的取舍
  （"改用现有原型硬套，文本描述保留你写的，但机制上其实是减伤/反打"），**不要重新发明
  闪避维度**，除非作者主动要求。

### buildSysBase 重构（重要，下次加新的 settleKind 要参考这个模式）

之前"送礼铁律"是直接堆在一个巨型模板字符串里的三元表达式，每加一个新场景就要再叠一层
三元，容易出现作用域引用错误（这次加送礼铁律时真的踩过一次：`cmd.match(...)` 写进了
`buildSysBase` 里，但 `cmd` 是 `act()` 内部变量，不在 `buildSysBase` 作用域）。这次重构把
逻辑抽成三个独立函数：

```js
function buildSettleNarrativeNote(o)   // narrativeOnly分支(双调用主叙事)该说什么
function buildSettleMvuNote(o)         // isSettle分支的MVU部分该怎么写
function buildSettleMvuExample(o)      // MVU示例指令
```

三个函数内部都是 `if (o.settleKind === "gift") {...} if (o.settleKind === "companion_invite") {...}`
这种平铺结构，**下次加新的伙伴/新的结算类型，只需要在这三个函数里各加一段 if，不要再往
巨型模板字符串里堆三元**。

`extractionEngine.js` 的 `callExtraction` 也做了同样的重构：`settleKind` → spec 的映射从
单一 if 改成了 `SETTLE_KIND_SPECS = { gift: "GIFT", companion_invite: "COMPANION_INVITE" }`
这张表，加新类型直接加一行。

## 四、第二阶段：2v2团战调度引擎（核心逻辑完成，commit `011e050`）

### 新建文件：`src/combat/teamBattleEngine.js`

职责：**不改 `resolveTurn.js`**（打磨过的1v1纯函数结算器，招式相克/伤害/状态判定全在
里面），2v2只是"调度层"——把"我方最多2人 vs 敌方最多2人"这一回合的行动，拆解成若干次
两两配对的 `resolveTurn` 调用。

### 单位对象结构（统一代替 DuelScreen.jsx 那种 player/npc 平铺变量）

```js
{
  id, name, side("ally"|"enemy"), alive,
  special, waigong, neigong, baseAtk, equipAtk, equipDef, equipEffects,
  hp:[cur,max], energy:[cur,max], statusSlots, movesetLocal,
  lastCounterSuccess, pendingAtkBonus, costPenalty, frozen, defenseBroken,
  lastStatusApplied, counterStacks, rebirthUsed,
}
```

### 核心导出函数

- `runTeamTurn(allyUnits, enemyUnits, intents)` —— 本回合调度入口。`intents` 是
  `Map<unitId, {move, targetId}>`。返回 `{ updatedAlly, updatedEnemy, turnLog }`。
- `resolveOneOnOne(attackerUnit, attackerMove, defenderUnit, defenderMove)` —— 单次1v1结算
  最小单元，内部调用 `resolveTurn` 并把结果写回两个单位对象（含 `applyEndOfTurnStatus`
  状态跳动伤害、复活特效、招式永久成长/降耗，跟 `DuelScreen.jsx` 的处理顺序完全一致）。
- `decideUnitMove(unit, battleState)` —— 复用现有 `decideNpcMove`，不重新发明AI决策。
- `decideUnitTarget(enemyUnits)` —— 托管单位选目标，纯随机（雪豹托管用这个）。
- `checkBattleOver(allyUnits, enemyUnits)` —— 一方全灭即结束。

### 【最重要】设计教训：裸奔规则

**第一版方案是错的**：最初想"两两配对分别跑 `resolveTurn`，防御方复用它自己的意图招应对
多次进攻"。Node测试立刻复现了bug——敌人A被玩家和雪豹先后攻击、自己又主动打玩家，结果
被扣了3次血而非2次，因为它自己的招在同一回合内被结算了3次（一次当它对玩家的主动出招，
一次当它对雪豹进攻的"防御方应对"）。

**根因**：`resolveTurn` 的三角相克模型（`judgeTypeMatchup`）从根本上假定"这两招是彼此
针对对方的"。不能直接把一个单位的招复用到它并未真正参与的多次配对里。

**正确设计**（已用3个Node测试场景验证）：每次A打B时，检查B这回合的招`targetId`是否
也指向A：
- 是 → 双方真对撞，标准 `resolveTurn(A的招, B的招)`
- 否（B在忙着打别人，或B的防御指定防的是别人）→ B在这次交锋里换成一个类型为 `STATUS`
  的空转招 `IDLE_STATUS_MOVE`（`energyCost:0`，无任何效果）。利用"攻击克状态"的既有相克
  规则，A的攻击自然必胜，B不会因为自己那招（其实是打向别人的）而对A产生任何反击/减伤
  效果——效果上就是"B对A裸奔"，且**完全复用现有相克代码，没有另开一条结算路径**。

这个换招只影响"A打B"这一次配对内部的计算，不影响B真正指向的目标那一次配对（B在那次
配对里仍然用它自己真正选的招）。

已验证的3个场景（测试脚本在git历史里，未留在仓库，下次要验证可以照 commit `011e050`
的commit message描述重新写一份Node脚本）：
1. 玩家+雪豹都打同一敌人，敌人反打玩家 —— 敌人应只承受两次真实攻击，不该多算
2. 敌人的防御指定了雪豹，玩家单独打这个敌人应"裸奔命中"
3. 玩家专心打A、敌人B同时打玩家（玩家没空理会B）—— 玩家对B应该也是"裸奔"（B的攻击
   全额命中玩家，玩家不会用"打A的那招"反过来跟B对撞）

三个场景全部验证通过，数值符合预期。
