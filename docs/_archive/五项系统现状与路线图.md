## 二、路线图（按依赖顺序排列，不是按重要性排列）

系统之间存在真实的前置依赖关系，顺序不能颠倒（比如名誉系统要汇总的
"事件"如果没有房间事件记录，就无源可汇总）：

```
第一阶段：补数据地基（无依赖，可立即开始）
├─ 1a. 24人的carry/levelCap/burdenMoveIds真正写入residentNpcs.js
│      （之前设计过方案，这次要真正落地代码，不是嘴上说说）
└─ 1b. 24人的fullBio逐个补完整（桑杰朵杰模式复制到剩余23人）

第二阶段：房间事件记录（依赖：无，但要跟第三阶段配合才有意义）
└─ 2a. 新增"房间事件日志"数据结构——记录"这个房间/这个据点，玩家
        最近做过什么"（比如"在猎户小屋跟老猎户切磋过""在库房偷过
        虎胆"），供AI对话时引用，让NPC看起来"记得"发生过的事

第三阶段：名誉/威望系统（依赖：无强制前置，但设计上应该参照总纲
"七方势力"这个既有框架，不要另起一套不兼容的新概念）
├─ 3a. 定义数值结构：七方势力（鱼定村/雪山派/喇嘛庙/玉泉寨/百花门/
│       欢喜教/锦官城/黑风寨——总纲原有势力列表)各自的声誉值，
│       正负区间待定
├─ 3b. 定义"什么行为改变声誉"——复用现有任务系统的flag机制
│       （比如任务奖励里加reputation字段，类似现有favorability加成
│       的写法），不需要发明新机制，只需要新增字段类型
└─ 3c. 接入对话prompt——让AI知道"玩家在这个势力眼里名声如何"

第四阶段：把三/四阶段的数据汇总进"记忆"注入（依赖：2a+3c都完成）
└─ 4a. 扩展本轮已经写的questStatusBlock模式，追加"房间事件"+
        "势力声誉"两块内容，一起注入system prompt，形成真正完整的
        "这个NPC此刻应该知道关于玩家的哪些事"
```

**为什么这个顺序**：名誉系统（第三阶段）不依赖房间事件（第二阶段）
就能独立跑通，但"记忆"这个概念（你说的第3项诉求）必须等房间事件和
名誉系统都有数据了，才有东西可汇总注入，所以第四阶段排在最后。第一
阶段（补数据地基）跟其他三个阶段没有依赖关系，可以随时并行推进，
不卡任何人的进度。
