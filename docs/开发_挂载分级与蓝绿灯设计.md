## 三、蓝绿灯分级设计

### 灯色定义（对齐酒馆语义）

> **勘误（2026-07-24）**：本节初稿把绿灯写成"状态判据触发"，那是错的。
> 酒馆里 **🟢绿灯的本义就是关键词触发**（见类脑 wiki《什么是世界书》§2 蟹堡王那个例子）；
> 用变量/状态控制注入的那套叫**变量系统**，是另一条路。下面按正确定义重写。

- **🔵 蓝灯（常驻 / constant）**：每轮必发，无条件。只放"少了就崩"的东西。
- **🟢 绿灯（关键词触发）**：扫描**玩家本轮输入 + 上轮引擎回复**（等同酒馆"扫描深度 2"），
  命中关键词才注入。
- **⚫ 灭灯**：未命中，一个字不发。

### 本项目的做法：绿灯走双通道，取并集

纯关键词有两个老毛病（《酒馆略进阶功能指南》已点破）：

1. 剧情该写某事、上文却恰好没出现那个词 → AI 缺资料，已读乱回；
2. 关键词反复出现 → 内容越滚越多，剧情推不动。

曲措乡有结构化状态（`room.npcs` / intent / flags），所以绿灯判据取并集：

```
关键词命中（文本信号）  OR  状态命中（系统确知的强信号）  →  点灯
```

这不是"用状态取代关键词"，而是**给关键词加一条兜底通道**——毛病①正好被状态通道补上：
玩家没说"梅朵"但梅朵就站在房里，`room.npcs` 知道，照样点灯。

`worldbook.js` 的 NPC lore 早就是这么做的（三源：在场 / 玩家输入 / 上轮回复），
本轮把同一套推广到世界观总纲（`gateScenario`）。

### 参照实现对比：姬侠传 `worldbook-engine.js`

本项目 `worldbook.js` 头注写着"借鉴姬侠传"，实读其源码后对比如下：

| | 姬侠传 | 曲措乡 |
|---|---|---|
| 匹配 | `indexOf` 纯子串 | 子串 + **别名** + 双向 includes 容错 |
| 触发源 | userInput + lastAIReply | **加"在场"结构化信号**（三源） |
| 常驻层 | 无 | 有（🔵蓝灯段） |
| 动作模板 | ACTION_REGISTRY 关键词选 12 套 | `inputIntent.js` 正则分类 + 动态字数预算（更准） |
| 预算/去重 | 无 | 按 scope 分档 |

结论：参照实现是纯关键词的最小版；本项目在两个轴上都已超出。本轮补的是它也没有的
**世界观总纲分条**。

### 新增档位：`settle`（结算叙事档）

**针对 §二 表 A 里那十余个"系统已结算完、AI 只演一句"的 handler。**

```
挂载 = 旁白身份 + 文体 + 格式铁律 + 篇幅 + [这一件既定事实] + 近 6 条 hist
schema = {"output":["行"],"memory":"≤50字"}
灭灯 = 物件志 / 认知隔离 / MVU / 全量schema / 远景 / 任务块 / lore全员
```

理由：这些轮**AI 无权改任何状态**——钱已扣、物已入袋、flag 已置。给它 delta/MVU
反而制造重复结算风险（现有 `forcedEventNote` 已在用大段文字告诫"不要重复结算"，
根子上就不该给它这个能力）。

预计单轮 system 从 ~8500 字降到 ~1200 字，**省 85%**。

| **玩家说"去熊山找虎胆"** | 1288 | 契诃夫之枪⟨词:虎胆⟩、规则补充⟨词:熊山⟩ |
| 战斗 | 1014 | 装备与掉落规则⟨态⟩ |

后两行是绿灯真正的价值：**玩家没点任何按钮、系统状态也没变，只因为文本里出现了那个词，
对应设定就自己亮了**——这是状态通道做不到的。

### 实施中发现并修掉的两个坑

1. **地图铁律差点被灭灯**：「不能创造新据点」原本埋在 scenario 的"规则补充"段里，
   一旦该段灭灯，AI 就可能凭空造据点——正是 §五 红线。已按项目既有惯例
   （硬性技术规范不受用户预设编辑影响）**提为硬编码蓝灯**，写进 `buildSysBase` 常驻区。
   顺带解决了"用户在设置面板删掉这段就崩"的老隐患。
2. **结算轮不该一刀切灭 lore**：送礼/拜师/成交这类结算牵涉具体某人，
   灭了人设那人就只剩个名字，写出来的对白没脾气。已改为 `settleNpc` 有值时保留
   lore 与「重逢」块。

## 五、不该省的地方（红线）

- **格式铁律**（「」包裹对话）：省了玩家分不清谁在说话，渲染直接崩。
- **成文铁律 proseRule**：占 D0 最强位，省了句子开始残缺。
- **在场 NPC 名单**：省了 AI 会凭空发明人，反幽灵过滤会把好感度全丢弃。
- **destinationLock**：省了 AI 乱编地点，与地图状态打架。
- **记忆四链写入**（S1 屏幕/S2 convo/S3 小纸条/S4 账本）：**任何档位都不能省**。
  轻档只砍"喂给 AI 的输入"，绝不砍"落库的输出"——省输入是省钱，省输出是失忆。

## 七、与酒馆世界书的对应关系（给后来者）

| 酒馆概念 | 本项目对应 |
|---|---|
| 🔵 蓝灯常驻 | `buildSysBase` 里无条件段 |
| 🟢 绿灯关键词触发 | **状态判据触发**（intent/在场/flags/面板来源）——更准，无"提了才想起"的偏差 |
| 位置：角色定义前/后 | system 内拼装顺序 |
| 位置：D0（最强位） | `userContent` 末尾的 proseRule / cmdSuffix |
| 扫描深度 | `contextWindow` / hist 窗口 |
| 条目开关 | scope 档位 + 各 Note 的生成条件 |

酒馆绿灯的老问题——「剧情要写某人了但上文没提名字，AI 已读乱回」——本项目天然免疫：
判据是系统状态（这个人在不在 `room.npcs`），不是文本里有没有出现字符串。
