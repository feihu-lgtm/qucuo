# 角色卡入册系统 · 设计与实测

> 这套系统的作用是把外部的 SillyTavern 角色卡导入曲措乡，让卡里的人物成为本作中
> 可对话、可切磋、有好感度的 NPC，或者成为玩家自己扮演的主角。
>
> **它的定位是内容映射器，不是运行时兼容层。**卡片提供的是内容（人设、关系、地理、
> 开场白），数值体系由本作自己提供。系统不会去复刻酒馆的注入引擎，也不会执行卡片
> 携带的任何脚本。
>
> 本文档的全部结论都来自八张真实卡片的实测，共计 142 条世界书条目。凡是与规范文档
> 冲突的地方，一律以实测为准，并在文中注明冲突所在。
>
> **代码位置**：`src/cards/`（解析、扫描、注册表）、`src/CardImportScreen.jsx`（界面）
> **改动史**：见 `src/version.js`

---

## 一、这套系统做什么，不做什么

### 1.1 要做的三件事

导入一张卡片的过程，本质上是三个动作的串联。

**第一步是剥离。**卡片里的前端脚本、变量系统、状态栏、格式指令、越狱段落，全部丢弃。
这些东西是卡片作者为酒馆那个无状态环境编写的补丁——酒馆没有房间、没有背包、没有任务
进度，所以作者只能用变量去模拟一个状态机。本作已经具备真正的状态机，再导入一套变量
系统，等于在已有数据库的系统里再塞一份电子表格。

**第二步是归化。**卡片的人设文本转成本作的 `npcLore` 条目，地理与规则转成 `gateScenario`
的分段，开场白转成 `OpeningSequence` 的入场文本，标注为玩家自身的条目转成第七位注入的
persona。这一步只搬内容，不改结构。

**第三步是赋值。**用本作自己的数值体系给导入的人物配上品阶、七维、随身物、招式、好感
初值。这一步由人工确认，AI 只提供草案。

### 1.2 明确不做的四件事

**不执行卡片携带的脚本。**`tavern_helper` 与 `regex_scripts` 一律忽略。实测中有一张卡的
前端脚本长达 41 万字符，并且其内容是从第三方网址动态引入代码。执行它等于允许任意远程
代码在玩家机器上运行。

**不复刻酒馆的世界书引擎。**酒馆的 `scan_depth`、`token_budget`、`recursive_scanning`、
`sticky`/`cooldown`/`delay`、`group_weight` 等机制不在本系统的实现范围内。本作的
`worldbook.js` 已有功能等价且更契合自身结构的三源触发机制，重建一套只会增加维护负担。

**不让 AI 决定数值的最终值。**AI 的产出一律标记为草案，每一项都附带判断依据，由玩家在
界面上逐项确认或修改。

**不从卡片抽取玩家的私密层体貌。**`bodyProfile` 的私密五项（疤痕印记、体味、身体细节、
敏感处、习惯癖好）只允许玩家手工填写，AI 抽取的输入与输出结构中都不包含这五个字段。

## 二、三个入口与使用流程

### 2.1 三个入口各自适用的场合

| 入口 | 位置 | 适用场合 |
|---|---|---|
| 开始界面「角色入册」 | `StartScreen.jsx` 的菜单项 | **导入主角必须走这里。**角色一旦创建完成，再导入主角就变成了覆盖 |
| 顶栏「🧾 入册」 | `TopBar.jsx` | 开局之后追加 NPC |
| 设置面板首页卡片 | `SettingsPanel.jsx` | 同上，另一条路径 |
| 快捷键 `I` | 全局监听 | 开局之后的快速开关 |

快捷键的避让规则写得比较严格：焦点位于输入框、文本域、下拉框或可编辑元素之内时不拦截，
按下 Ctrl、Cmd、Alt 中任一修饰键时也不拦截。否则玩家在输入框里打出字母 i 就会弹出窗口。

### 2.2 为什么导入主角必须在开局之前

`MudRPG.jsx` 的渲染顺序是三级提前返回：先判断 `showCharCreate`，再判断 `showOpening`，
最后才渲染游戏主界面。新开局时第一个判断即成立，函数在那一行就返回了，主界面之后的设置
面板与全部浮层都不参与渲染。

因此开始界面的入册窗口挂载在 `main.jsx` 这一层，不经过 `MudRPG`。玩家在开始界面导入的
主角会存成一张「待用卡」（存于 localStorage，因为 `CharacterCreate` 是同步渲染，读不了
异步的 IndexedDB），`CharacterCreate` 读到这张卡后会询问玩家是否用它开局。这张卡是一次性
的，无论用与不用，提交时都会清除。

### 2.3 完整流程

```
拖入卡片 → 解析（纯代码，不花调用）
        → 先认人（一次 AI 调用，可跳过）
        → 勾选名单（玩家决定要哪些人）
        → AI 扫描（换算数值，可跳过）
        → 逐项审改（玩家定稿）
        → 落册
```

其中「先认人」与「AI 扫描」都是可选按钮，不是必经关卡。解析阶段结束后，所有必填字段
都已具备兜底值，玩家完全手工填写也能完成入册。这样设计的原因是免费反向代理随时可能
返回 429 或超时，外部服务失效不应该导致玩家连导入都无法完成。

NovelAI 那两张图值得单独说明。它们各自携带六个文本块（`Description`、`Software`、

八张真卡。因此判定卡片既不能靠「有文本块就当卡读」，也不能靠文件体积。唯一可靠的判据是
文本块的关键字是否精确等于 `ccv3` 或 `chara`。

### 3.4 三种截然不同的卡片形态

实测样本呈现出三种形态，它们对系统的要求完全不同。

**第一种是世界书驱动型。**六个经典文本字段基本为空，全部内容写在 `character_book` 的
条目里，靠关键词点亮。八张卡中有六张属于此类。系统以此为主入口。

**第二种是传统写法型。**六个经典字段填得很满，世界书作为补充。魔门宗主萧月寒那张即是
此类，它的 `personality` 有 929 字、`scenario` 有 383 字、`mes_example` 有 1181 字。
本系统对这一类保留了六字段兜底路径。

**第三种是模具卡。**万象枢机属于此类。它的 28 条世界书条目大多为空、全部处于关闭状态，
角色名字段的内容是字面量 `{{char}}` 而非人名，真正干活的是那份 41 万字符的前端脚本加上
配套的 138 条预设。这种卡片不是一个角色，而是把整套前端应用塞进了 PNG 文件。系统会识别
并拒收它，判据是三个信号同时成立：世界书条目全部关闭、条目内容多半为空、脚本体积占卡片
过半。

## 四、解析层：卡片的真实形态与容错

代码位于 `src/cards/cardParse.js`。文件头部以 F1 至 F18（字段容错）与 R1 至 R5（拒收规则）
编号列出全部容错点，每一条都注明来源于哪张卡的实测。以下只说其中最关键的六条。

### 4.1 载体版本与 spec 字段互不相干

哀鸿城破十日记那张卡只有 `chara` 文本块，没有 `ccv3` 文本块，属于第二版载体；但它的
JSON 内部 `spec` 字段写的是 `chara_card_v3`。因此不能靠文本块的名字推断规范版本，也不能
靠 `spec` 字段推断载体形态，两者必须分别读取。

另外实测七张双文本块的卡片，其 `chara` 与 `ccv3` 两份数据的字节完全相同。规范要求两者
同时存在时优先采用 `ccv3`，照办没有成本，但实际上没有差别。

### 4.2 真正的位置信息不在规范字段里

规范定义的 `entries[].position` 只有 `before_char` 与 `after_char` 两个取值，它表达不了
「按深度注入」这种位置。酒馆把真正生效的位置放在 `extensions.position`，那是一个数字
枚举：0 表示角色定义之前，1 表示角色定义之后，4 表示按深度注入。

**这两者会互相矛盾。**断法大陆那张卡的 36 条条目，规范字段全部写着 `after_char`，而内部
字段显示有 13 条实际位于 `before_char`。142 条中共有 22 条不一致，占 15%。

系统的处理方式是：一律以 `extensions.position` 为准，规范字段仅用于统计冲突数量并在
体检报告中提示。

### 4.3 承载实际行为的是 extensions 里的四个字段

每条条目的 `extensions` 对象包含三十个左右的酒馆私有字段，但实测中 `probability`、
`sticky`、`cooldown`、`delay`、`group` 全部保持默认值，无人使用。真正有信息量的只有四个：
`position`（真实位置）、`depth`（注入深度）、`role`（以哪种身份注入）、以及次要的
`exclude_recursion` 与 `prevent_recursion`。

`extensions` 的键数量并不固定，实测出现过 21、30、31 三种。因此读取时必须逐个带默认值，
不能假设任何一个键存在。

春明子那张卡里有一处技法值得学习：它把角色本体的人设放在 `position=4`、`depth=0`、
`role=user` 的位置上，也就是以玩家身份贴在对话的最末端，而不是放进系统提示词的顶部。
这样做可以避免人设被冗长的历史记录稀释。这个位置对应本作的第十一位注入。

### 4.4 use_regex 与 selective 两个字段都不可信

`use_regex` 在 142 条中有 127 条为真，占 89%。但哀鸿城破十日记那张卡的 15 条条目全部为假。
所以这个字段既不能一概无视，也不能照规范执行。

按规范，`use_regex` 为真时应当把关键词当作正则表达式处理，并且忽略 `constant` 与
`secondary_keys`。如果照办，断法大陆那三条 `constant` 为真、关键词为空的「世界基石」条目
就永远不会命中，整个世界观都注入不进去。

系统的处理方式是：判定常驻只看 `constant` 与关键词是否为空，不看 `use_regex`。

`selective` 的情况类似——142 条中有 51 条为真，但 `secondary_keys` 非空的条目数量是零。
这个字段从来没有真正生效过，直接忽略。

### 4.5 关键词里的逗号连写会让条目永不命中

逐玉那张卡的 15 条条目中有 10 条，其关键词数组的内容形如 `['齐旻，阿旻']`。

作者的意图显然是给出「齐旻」和「阿旻」两个别名。但按规范，关键词数组的每个元素都是一个
独立的关键词。酒馆会拿「齐旻，阿旻」这个带全角逗号的完整字符串去匹配对话内容——除非玩家
原样打出这七个字，否则永远不会命中。

**这个错误作者无法察觉**，因为这十条全部是 `constant` 为真的常驻条目，关键词写废了但注入
照常发生，效果上看不出问题。

这条缺陷同时影响本作。`worldbook.js` 的在场判定使用双向包含容错，恰好能兜住这种脏值；
但「被提及」判定使用的是 `scanText.includes(k)`，玩家输入「我去找齐旻」时，
`scanText.includes("齐旻，阿旻")` 恒为假，会静默漏掉。

系统的处理方式是：入库前把关键词元素按中英文逗号、顿号、分号、斜杠再切一次。

### 4.6 关键词里可能是宏

封神异闻录的玩家设定条目，其关键词是 `['<user>']`。这是合法写法，但匹配之前必须先把宏
展开成实际的角色名，否则同样永不命中。

系统会在展开宏之前先把原始关键词保存在 `keysRaw` 字段里。这是必要的——展开之后
`<user>` 会变成玩家的名字，如果不留下原始形态，这条「玩家自身设定」就会被当成一个以玩家
名字命名的 NPC 导入进来。

### 4.7 单条条目的长度需要设闸

哀鸿城破十日记有一条名为「林翩翩相关原文」的条目，长度为 27294 字符。万象枢机有一条
长达 29492 字符。142 条中超过一万字的有六条。

一条命中就往提示词里灌两万多字，单轮的 token 预算会当场穿底。系统的处理方式是：超过
8000 字的条目默认不导入，在体检报告中列出，由玩家决定是否手工挑选段落。

## 五、AI 认人与扫描

代码位于 `src/cards/cardScan.js`（流程编排）、`src/cards/scanPrompts.js`（提示词与清洗）、
`src/cards/rateLimiter.js`（限流）、`src/cards/scanStore.js`（断点与缓存）。

### 5.1 先算清哪些工作不需要 AI

设计之初的约束是免费反向代理每分钟只允许五次调用。因此第一步是把不需要 AI 的工作全部
剔除。

| 工作项 | 由谁完成 |
|---|---|
| 姓名与别名 | 代码（取关键词的第一项与其余项） |
| 一句话身份 | 代码优先（条目备注不超过 15 字则直接采用），超长才交给 AI |
| 好感度初值 | 代码（默认为零） |
| 里程碑两档 | 代码（套用固定模板兜底） |
| 气血上限 | 代码（`hpFromNeigong` 公式计算） |
| 随身物 | 代码（四池随机，按身份、地域、品阶抽取在册物品） |
| 招式 | 代码（原型乘品阶自动解出） |
| 立绘 | 代码（PNG 本体图） |
| 条目分类 | 代码先做保守初判，AI 再覆盖 |

剔除之后，真正必须由 AI 完成的只剩七件：疑难条目的分类、一条塞多人的拆分、超长人设的
一句话压缩、品阶判断、七维数值判断、玩家体貌公开层的拆条、开场白的人称与文体归化。

### 5.2 令牌桶而不是定时等待

限流采用令牌桶算法：桶容量为五，每十二秒补充一个令牌。这样连续五次调用可以突发跑完，
之后才开始排队；而只需要两次调用时不必干等二十四秒。

桶的状态存于 localStorage，刷新页面后额度依然有效。否则玩家一刷新就能重新获得五次额度，
随后必然撞上服务端的 429。

结算时有一处细节：补充令牌后，时间戳只推进到已经兑换成令牌的那一部分，不足一个补充周期
的毫秒数保留下来继续累积。如果直接把时间戳置为当前时刻，这些零头会被抹掉，连续多次小额
调用下实际速率会慢于额度。

### 5.3 四个阶段

**阶段一是认人与归类。**输入是每条条目的备注、关键词、机器初判结果，以及正文。一次调用
解决四件事：确定每条的最终分类、认出写的是同一个人的多条条目、认出一条里塞了多个人物、
概括卡片的题材。

这一阶段原本只发送每条的前 120 字摘要，目的是节省额度。但反向代理不计费，省下的那点
token 换来的是判断错误——「三霄」「血角」这类备注与关键词完全相同的条目，只看开头 120
字根本分不出是人物还是概念，而这恰恰是最需要 AI 帮忙的一类。现已改为发送正文。

不过也没有直接发送全文，原因与费用无关，而是两个硬性限制：反向代理对单次请求的体积
通常设有上限；实测存在单条 27294 字、整卡 133095 字的世界书。发送全文会让一次分类耗时
数十秒，还可能被网关直接拒绝。折中方案是单条上限 3000 字——一条人物设定的前 3000 字
必然已经写清了「这是谁」，分类所需的信息全在开头。整卡再设 90000 字的总量上限，超出时
按条目均摊而不是先到先得；先到先得会让排在前面的巨型条目吃掉全部配额，后面的人物条目
一个字都发不出去。

改为发送正文后的实测输入量：春明子 3886 字、封神异闻录 8549 字、逐玉 11982 字、
断法大陆 21452 字、哀鸿城破十日记 33215 字。最大者为 33 KB，Gemini 的上下文窗口与反向
代理的请求体限制都能容纳。

**阶段二是人物换算。**只对分类为人物的分组执行，输入是合并后的完整人设正文，输出包括
一句话身份、品阶建议、七维数值、外貌锚点、初见态度、好感初值、两档里程碑。每批默认
四人。

**阶段三是玩家档案。**只在「这张卡当我自己」被勾选时执行，输出体貌公开层的七个字段、
七维数值、出身来历。私密五项不在输出结构中。

**阶段四是开场白归化。**只改写玩家选中的那一个开场白。`npcLore` 正文不改文体——那是给
模型看的内部资料，不是给玩家看的正文，改写纯属浪费额度。

### 5.4 判断品阶与七维需要参照系

品阶是零到五的六档，七维是零到十的整数。这些纯数值如果不给参照系，模型只能凭空猜。

因此提示词中的锚点全部取自本作的实际配置，而非编造的描述。品阶的六档各自列出
`residentNpcs.js` 里真实存在的人物作为例子：零档是抄经八十七天还没摸过剑的入门弟子、
索桥上蹭住的野道士；一档是村长之女、饭馆掌柜、村口一只好斗的大公鸡；五档是青城派掌门、
唐门家主、熊山的吊睛白额巨虎。数值口径则对齐 `getTierPower` 的实际取值。

提示词中另有一条明确要求：拿不准就往低判。判高了会让杂鱼被写得深不可测，比判低更糟。

### 5.5 每个字段都必须附带判断依据

AI 输出的每一项数值都配一个不超过二十字的依据字段，例如「品阶三档，依据：正文称其为
北境公爵、麾下三千甲士」。界面上把这些依据显示在对应字段旁边。

没有依据，玩家就只能盲目相信，那么「AI 抽草案、人工逐项改」这个设计就退化成了「AI 说了
算」。依据字段的成本可以忽略，收益是玩家真的能判断。

### 5.6 熔断：区分两种失败

解析失败分两类，它们的补救办法完全相反。

一类是输出被截断：模型确实在输出 JSON，但被 `maxTokens` 切断了，特征是文本中有左花括号
却没有闭合。这种情况把批次拆小重跑能解决，值得再花额度。

另一类是模型压根没有输出 JSON，例如回了一句「抱歉，我无法完成」。这是模型能力或提示词
的问题，拆小一百次也一样。

**不区分这两类的后果实测过。**第一版的降级链是「四人一批失败就拆成两人，再失败拆成一人」，
每级还带一次重试。用「模型永远回绝」的模拟接口跑一张三批的卡：预算四次，实际烧掉
21 次调用。在每分钟五次的额度下这是四分多钟，而且全部花在必定失败的重试上。

现在的处理方式是：截断类拆小重试；非 JSON 类不重试，并且连续两批都如此就全局熔断，剩余
批次直接采用兜底值。同一个模拟接口现在只花五次。

### 5.7 断点续传与缓存

每一批的结果一拿到手就立刻写入 IndexedDB，不在内存里攒着。扫描一张大卡需要四到六次调用、
一分多钟，中间任何一次超时或 429 都可能中断；如果结果只在内存里，中断就等于把已经烧掉的
额度全部扔掉。

缓存以卡片指纹为键。指纹的计算纳入了每条条目的备注、长度与关键词，因此修改过世界书的
同名卡片不会误命中缓存。同一张卡重复扫描时调用次数为零。

### 5.8 实际预算

| 卡片与选项 | 阶段一 | 阶段二 | 阶段三 | 阶段四 | 合计 | 约需时间 |
|---|---|---|---|---|---|---|
| 断法大陆，全跑加当主角 | 1 | 4 | 1 | 1 | 7 | 24 秒 |
| 断法大陆，勾选五人加当主角 | 1 | 2 | 1 | 1 | 5 | — |
| 断法大陆，只导一个 NPC | 1 | 1 | 0 | 0 | 2 | — |
| 封神异闻录，全跑加当主角 | 1 | 1 | 1 | 1 | 4 | — |
| 魔门宗主，当主角（人设在六字段，无人物条目） | 1 | 0 | 1 | 1 | 3 | — |
| 万象枢机 | 拦截，一次不扫 | | | | 0 | — |

### 5.9 为什么认人必须在勾选之前

这是一处时序错误，修正之前的链路是：机器初判 → 玩家在勾选界面确定名单 → 点击扫描 →
阶段一执行 AI 分类 → 阶段二换算。

而人物分组函数的末尾有一道按勾选名单的过滤。于是 AI 认出「血角」是人物，但玩家在勾选
界面看到它挂在「待定」栏里没有勾选，它就被过滤掉了。AI 白认一场。

八张卡中落在「待定」栏的真实人物包括：血角、岩蹄、铁角（断法大陆）；金灵圣母、三霄
（封神异闻录）；俞宝儿、樊长玉、谢征（逐玉）。它们的共同点是备注与关键词完全相同，
机器的判据（要求备注不等于第一个关键词、但包含它）够不着。

修正后的做法是把阶段一提前，做成拖入卡片后的一个「先认人」按钮。结果写入同一个缓存槽，
之后点击「AI 扫一遍」不会重复调用，**总预算不变**。认完之后名单整个换成 AI 那一份，不再
分「候选」与「待定」两栏；认出来的默认全部勾选，玩家可以逐个取消——最终否决权不交给 AI，
因为它确实会把地名认成人物。

### 5.10 机器初判保持保守，没有放宽

既然 AI 会覆盖机器初判，看起来可以把判据放宽一些。但机器初判是 AI 失败时的兜底。免费
反向代理随时可能返回 429，兜底宁可少认几个人，也不要把「人间共主」「混血儿·处境与能力
规律」这类概念当成活人写进叙事。

## 六、落脚：不落地、驻场、游走

导入的人物是否会真的出现在世界上，由玩家在入册时选择。三种方式各自对应本作已有的一套
机制。

| 方式 | 对应机制 | 行为 |
|---|---|---|
| **不落地**（默认） | 只进 `npcLore` | 人设在被提及时注入，人物不会主动出现在任何据点。适合远方的人、传闻里的人 |
| **驻场** | 等同 `residentNpcs.js` | 选定一个据点，玩家进入该据点必定遇见，不受时辰与概率影响。可再锁定一个内层房间 |
| **游走** | 等同 `npcPool.js` | 给若干据点分配权重，再设定时辰区间，按权重每天随机出现 |

默认为「不落地」是有意的选择：**导入一张卡片不应该擅自改变世界上有谁在哪里。**玩家要让
某人真的出现，就明确指定。

三处实现细节值得说明。

**游走的随机源使用 `seededRand(天序, 人名)` 而不是 `Math.random`。**同一天进出据点会反复
重新计算，若用真随机，一个游走的人物会在玩家走进走出之间闪现。

**驻场者一并纳入 `commitRound` 的幽灵过滤名单。**驻场人物有固定归属，不应该被 AI 在别的
据点凭空刷出来。否则玩家在鱼定村入册的人，可能在锦官城冒出一个同名者。

**配置无效时自动降级为不落地。**选了驻场但没有指定据点、选了游走但没有给任何据点权重，
这两种情况都退回「不落地」，而不是产生一个永远不会出现的幽灵配置。

## 七、数据流：从卡片到游戏

### 7.1 入册库独立于存档

已入册的角色存于 `src/cards/importedRegistry.js`，走独立的 IndexedDB 库，与 `saves.js`
平行。这与 `presetSystem.js` 里那个「独立于任何单个预设的全局片段库」是同一个思路：导入
的卡片属于玩家的资产，不属于某一局游戏的状态。

存进存档会带来两个麻烦：读取旧存档时导入的人物凭空消失；每个存档槽位各存一份同样的人设。

### 7.2 三条读取路径

```
importedRegistry
  ├─ getImportedNpcLore()          → roundNotes.js 的 combinedNpcLore
  │                                  （预设 ＋ 驻场表 ＋ 入册，三来源合并）
  ├─ getImportedMilestones()       → characterMilestones.js
  │                                  （用 attach 惰性合并，避免循环引用）
  ├─ getImportedSignatureMoves()   → npcGeneration.js 的专属出招表
  │                                  （入册优先于内置，未配招式者回退按品阶随机）
  └─ getImportedForDistrict()      → MudRPG 的 toInject（第五个来源）
                                     数值经 toPoolLike 转成 npcPool 条目形状
```

### 7.3 好感度初值为零的人物不写入变量树

只有 AI 判定「已有交情」（初值不为零）的人物才写入 `varTree`。写入之后这个人物就会出现
在「人物关系」页面，而一个还没有见过面的人出现在关系页面是不对的。初值为零的人物等到
自然相遇再建立交情。

### 7.4 字段白名单是一处反复踩的暗礁

`toRoomNpcWithCombat` 用一份字段白名单把 `npcPool` 条目转成 `room.npcs` 条目，而
`toRoomNpc` 只保留 `id`、`name`、`brief`、`isPoolNpc`、`carriedItems` 五项。不在白名单
里的字段会被静默剥掉。

已经踩到两次：`special`（七维）与 `moveset`（招式）都曾不在白名单里。这两项对本作原有
代码没有影响——驻场表里 `special` 出现零次，全部走随机生成——但入册人物的七维是玩家在
界面上一格一格调过的，剥掉等于白调。

因此新增任何需要传递到 `room.npcs` 的字段时，都必须同时检查这份白名单。

## 八、踩过的坑

这一节记录设计与实现过程中犯过的错误，包括判断错误与工程错误。保留它们的目的是让后来者
不必重犯。

### 8.1 三张卡就下结论，第四第五张翻案

看过三张卡之后，我得出结论：「六个经典文本字段已被弃用，`personality`、`scenario`、
`mes_example` 全部为零，可以判死。」

第四张与第五张卡立刻推翻了它。魔门宗主萧月寒那张的 `personality` 有 929 字、`scenario`
有 383 字、`mes_example` 有 1181 字，五项俱全。

同一轮里还有四条结论一起翻案：`use_regex` 恒为真、两个文本块总是同时存在、
`entry.extensions` 是固定 31 键、卡级 `extensions` 必有 `depth_prompt`。

**教训是样本量与置信度必须挂钩。**现在的做法是把结论分成两栏：「八张卡一致、可以写进
代码的硬结论」与「样本不足、仅作观察的软结论」，并在文档里标明。

### 8.2 熔断缺失导致额度失控

见 5.6。预算四次的活干成了 21 次。根因是把「输出被截断」与「模型不吐 JSON」混成了一种
失败来处理。

### 8.3 玩家自己变成了 NPC

AI 在阶段一把整卡条目全部判成人物时，玩家的 `<user>` 设定条目会被展开成玩家名字，然后
作为一个以玩家命名的 NPC 混进人物名单。

修正方式是：分类为「玩家自身」的条目按机器初判硬性排除，不看 AI 的判断。玩家自己绝不能
变成一个 NPC，这条不需要 AI 参与决策。

### 8.4 里程碑阈值搞错了档数

我按 30、55、75、95 四档设计了提示词，而本作的 `getAvailableMilestone` 只查询 60 与 30
两档。给出其他阈值等于永远不会解锁。

更严重的是每档还有一个 `text` 数组，`CharacterPage.jsx` 里直接对它调用 `.map()`，
若为 undefined 会当场抛出异常。

**教训是接入既有系统之前必须读完它的读取侧代码**，不能只看数据结构就动手。

### 8.5 注入结构面板里那一栏一直是空的（既存缺陷）

`MudRPG.jsx` 里调用 `matchNpcLore` 时传的是 `(preset, 字符串, 数组)`，而函数签名收的是
`(npcLore 数组, ctx 对象)`。第一个参数不是数组，函数第一行的 `Array.isArray` 判断就返回
空数组。

因此「注入结构」审计面板中「人设注入」那一栏，不管场上有谁都显示「本轮无在场者需注入
人设」。真实的注入链路在 `roundNotes.js`，那边的参数是正确的，游戏运行不受影响，只是面板
在骗人。

### 8.6 入册入口挂错了层

入册界面原本挂在 `GlobalOverlays` 里，而那一层在新开局时压根不参与渲染（见 2.2）。从开始
界面点「设置」，玩家看到的是角色创建页，设置面板根本没有出现。

更根本的错误是：导入的卡片要当主角，只能在角色创建之前使用，而我把入口全部放在了游戏
之内，等于把一个开局前的功能放在了开局之后。`StartScreen.jsx` 在 `main.jsx` 里、在
`MudRPG` 之外，我一开始查接入点时只在 `MudRPG` 里检索，压根没有往上一层找。

### 8.7 不带校验的字符串替换，犯了两次

用脚本改文件时使用了不带校验的字符串替换。锚点对不上时替换静默空转，脚本照样打印「已
完成」。

第一次是设置面板的入册卡片。第二次是待用主角卡的三个函数——消费侧（`CharacterCreate`
三处读取、`main.jsx` 一处写入）提交了，生产侧压根没有进仓库。

现在的做法是两头都卡：替换之前断言锚点存在，替换之后断言结果里含有新内容。

### 8.8 测试全绿而构建是坏的

上一条那个断链，`vitest` 643 条测试全绿，只有 CI 的 `vite build` 报出
「`getPendingPlayerCard` is not exported by `importedRegistry.js`」。

原因是 643 条测试里没有一条 `import CharacterCreate.jsx`。两个文件各自语法都合法，
A 引用了 B 没有导出的名字这种事，只有真正打包解析模块图时才会暴露。

本项目早先栽过同源的一次：`version.js` 写坏了引号，测试没有一条 import 它，于是测试全绿、
构建失败。同一个坑换个文件重演。

补救措施是 `scripts/bundleCheck.sh`，用 `esbuild --bundle --packages=external` 把
node_modules 外部化，不装依赖就能解析项目内全部相对引用，专门抓导出缺失、路径写错、
循环引用。这个脚本不是 `npm run verify` 的替代品——装了依赖就该跑 verify。

验证这个脚本本身时用的是反例：先把某个导出临时改名，确认它确实报错，再改回来确认零错误。
检查手段自己也要被验一遍。

### 8.9 文档统计行的三个数字全部过期

`docs/文件树.md` 头部那行声明文件总数的话被守卫盯着，加了七个文件后对不上，CI 变红。而
`docsTree.test.js` 里相关的守卫有三条，我只手工核了自己知道的那两条就断言「已核过」。

顺带发现那一行的三个数字全部过期：文件数、测试份数、非测试代码行数。后两个守卫不检查，
所以一直在漂。

### 8.11 props 没传就用，构建与测试都抓不到

审改面板拆成 `ReviewPane` 子组件之后，它的 props 解构里没有 `apiCfg`，而函数体内写了
`<ReviewNpc apiCfg={apiCfg} />`。

两个文件各自语法合法，模块图也解析得通，于是构建绿灯上线。玩家扫描完切到审改页，页面
直接白屏，控制台只有一句 `apiCfg is not defined`。643 条测试也测不到——没有一条会渲染
这个组件。

**这是第三类问题。**前两类构建能抓（`version.js` 写坏引号、import 了不存在的导出），这一类
构建完全成功，只在运行时抛 ReferenceError。

补救措施是 `scripts/propsCheck.mjs`：扫描全部 jsx 文件，找出形如 `attr={someName}` 的 JSX
属性，检查那个标识符能否在所属组件的作用域链里解析。它花了三轮才做到零误报，每一轮的
误报都是我自己的实现缺陷：

1. 模块作用域只收集到「第一个顶层 function 之前」，漏掉了放在文件末尾的样式常量
   （`topBtn`、`carArrow`）
2. 提取标识符时用 `^[A-Za-z_$]` 锚定开头，箭头函数的嵌套括号让捕获结果形如 `(sk, i`，
   首字符是括号于是整段被丢弃，`.map((sk, i) => …)` 的参数全部收不到
3. 多行 import 的续行有缩进，被顶层过滤滤掉，`selStyle` 这类从共用零件文件引进来的
   名字丢失

最终状态：1458 个 JSX 属性、70 个 jsx 文件，零误报；把 `apiCfg` 从 props 里去掉能精确
报出那一处。**一个会误报的检查工具不会有人用，所以校准它本身值得花这三轮。**

### 8.10 一整轮的重复劳动

在不知道 `combat/moveArchetypes.js` 存在的情况下，我读着旧的 `MOVE_POOL` 做了一个招式
编辑器，让玩家逐个勾选特效标志位、填写数值。

而本作的招式效果由「原型乘品阶」自动解出：同一个「防守反击」，白档只是挡一下，红档是
听桥——近乎全免加满反打加抢先结算。玩家该决定的是「这人走哪条路数」，不是逐个数值。逐
字段编辑会绕过原型系统，产出平衡之外的怪招。

这一轮的产出全部作废并撤销。**根因是开工之前没有同步仓库、也没有检索既有实现。**现在的
做法是每轮动手之前先 `git fetch` 并检索相关关键词。

## 十、还没有做的

**入册人物的随身物无法精确指定到内层房间归属。**驻场可以锁定内层房间，游走的落点由现有
的种子随机逻辑分配，但没有提供「此人白天在 A 房、夜里在 B 房」这种排班。

**卡片的世界观条目（势力、地点、规则）虽然分类出来了，但导入路径尚未完全接通。**目前
`onImportWorld` 已有接口，落地环节还需要与 `gateScenario` 的分段结构对齐。

**没有导入历史的管理界面。**`listImported` 与 `removeImported` 已经具备，但界面上没有
「查看已入册的人、删掉某一个」这样的入口。

**多张卡片之间的同名冲突只做了覆盖，没有做提示。**后导入的同名人物会直接覆盖先导入的，
界面上不会提醒玩家。

## 附录：如何自己扫一遍卡库

```bash
python3 scripts/card_probe.py ~/SillyTavern/data/default-user/characters
python3 scripts/card_probe.py ./cards --json out.json
```

这个脚本零依赖，Python 3.8 即可运行。它不打印任何 `content`、`description`、`first_mes`
的正文，只输出字段名、长度与枚举值的分布，因此扫完可以把输出整段贴出来而不泄露卡库内容。
不是角色卡的 PNG 会自动归入「非角色卡文件」一栏，不会中断扫描。

脚本还会单独列出两类脏值：关键词元素内含分隔符的（在酒馆里几乎永不命中），以及关键词
元素内含宏的（匹配前必须先展开）。
